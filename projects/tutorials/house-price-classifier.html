Tutorial 3 - House Price Band Classification

Project Overview

Estimating a house's exact sale price is the textbook regression task. But many real business questions are coarser: is this listing cheap, medium, or expensive? This project takes a synthetic housing market and turns price prediction into a 3-class classification problem - showing when and why you would do that, how to build labels from percentiles, and how to keep a synthetic pipeline leak-free.

Synthetic Dataset

The data generator (seeded, so runs are reproducible) creates 1,200 houses with four features and a ground-truth pricing formula:

FeatureRangeEffect on price
sqft500..3500+120 per sqft
bedrooms1..6+8,000 each
age0..80-900 per year
locationScore1..10+15,000 per point
price = 120*sqft + 8000*bedrooms - 900*age + 15000*location
        + noise(N(0, 25000))
price = max(price, 50000);   // clip unrealistic lows

Pros of synthetic data: no download or licensing, known ground truth for debugging, full control over size and difficulty. Cons: the model can only learn the formula you wrote - it will never surprise you with a real-world interaction your simulator lacks, and results are optimistically clean.

Regression vs Classification Framing

  • Regression outputs a number ($412,733). It preserves maximum detail but demands more from the model and makes mistakes hard to summarize.
  • Classification into bands outputs a category. It matches decision-making language (“bargain”, “market rate”, “overpriced”), tolerates pricing noise (the exact dollar figure is often arbitrary), and lets us use cross-entropy with our Sequential stack.

We classify here deliberately: banding absorbs the ±$25k noise we injected, so classes are far more learnable than raw prices.

Tertile Labeling (Done Right)

To define cheap/medium/expensive without guessing thresholds, split the training prices at their 1/3 and 2/3 quantiles:

double[] sortedTrainPrices = trainPrices.clone();
Arrays.sort(sortedTrainPrices);
double t1 = sortedTrainPrices[trainN / 3];       // ~33rd percentile
double t2 = sortedTrainPrices[2 * trainN / 3];   // ~67th percentile
// label = price <= t1 ? 0 : (price <= t2 ? 1 : 2)

Critical detail: thresholds come from the training split only, then are applied unchanged to the test split. If test prices influenced the thresholds, label information would leak from evaluation data into training - inflating accuracy that evaporates in production. The same rule applies to the standardization statistics below.

Pipeline and Model

  1. Generate 1,200 rows with seed 42.
  2. Seeded shuffle, then a 70/30 split (840 train / 360 test).
  3. Compute tertile thresholds + feature means/stds on the train half.
  4. Label both splits with those thresholds; standardize both with train stats: (x - mean) / std.
try (Sequential net = new Sequential(Optimizer.adam(0.01f),
        new Input(4),
        new Dense(24), new ReLU(),
        new Dense(12), new ReLU(),
        new Dense(3))) {

    net.fit(trainX, trainY, 200, 32, testX, testY, true);
}

Standardization matters even more than usual here because sqft (~2000) and locationScore (~5) differ by three orders of magnitude; unnormalized, gradient descent would take wildly mismatched step sizes per weight.

Evaluation

Metrics.printReport prints accuracy plus per-class precision/recall/F1 from the confusion matrix. Expected result after 200 epochs:

Accuracy:  0.85
              0     1     2
  0         113     9     0     cheap almost never called expensive
  1          15    91     5     medium bleeds into both neighbors
  2           0    25   102     expensive sometimes called medium

All remaining errors sit on the diagonal neighbors - nothing jumps from cheap straight to expensive. That is expected: houses near a tertile boundary genuinely straddle two bands, so those mistakes are mostly labeling artifacts rather than model failure.

Exercises

  1. Increase the noise standard deviation to 50,000 - which class pair gets confused first?
  2. Switch to quartiles (4 bands). Does accuracy drop simply because the boundaries are tighter?
  3. Add a useless random feature (e.g. house color as a float). How much does it hurt?
  4. Compute tertile thresholds over ALL rows instead of train only - measure the leakage effect on reported accuracy.

Tutorial 9 - Credit Card Fraud Detection

Project Overview

Detect fraudulent card transactions from five behavioral features. The dataset is generated in code (seeded, fully reproducible) so you can study the one thing real fraud data always has and toy datasets never show properly: extreme class imbalance - here only ~3% of transactions are fraud. This tutorial is a deep dive into why plain accuracy lies in that regime and which numbers to read instead.

Synthetic Data Generation

With new Random(7) we draw 6,000 legitimate transactions and only 180 fraudulent ones:

static double lognormalAmount(Random r, double scale) {
    return Math.max(2.0,
            Math.exp(Math.log(40) + r.nextGaussian() * 0.75) * scale);
}

Rows are then seeded-shuffled and split 70/30 (4,326 / 1,854), and all five features are z-score standardized with training-set statistics. Note the deliberate overlap: a few frauds look perfectly normal (small daytime purchases near home), which is exactly what makes the metrics interesting.

Why Raw Accuracy Misleads

The majority class baseline is the number to beat only if you care about accuracy:

"Always predict normal" -> 96.98% accuracy ... and ZERO frauds caught.

A model that scores 99.78% accuracy can still miss money. So after Metrics.printReport the project computes fraud precision and recall explicitly from the 2×2 confusion matrix (conf[true][predicted]):

  • Fraud recall = TP / (TP + FN) - share of actual frauds we catch. Every miss is direct financial loss.
  • Fraud precision = TP / (TP + FP) - share of alarms that are real. Every false alarm costs an analyst review or an angry customer.
  • F1 balances the two when no business cost matrix is available.

Typical run at the default arg-max threshold (P(fraud) ≥ 0.50):

fraud recall=0.93 precision=1.00 f1=0.96 (missed=4, false alarms=0)

Threshold Shifting

The arg-max cut-off is arbitrary. Because the output is a calibrated probability we can move the decision threshold and slide along the precision/recall frontier:

threshold P(fraud)>=0.50 -> recall=0.93 precision=1.00
threshold P(fraud)>=0.35 -> recall=0.93 precision=1.00
threshold P(fraud)>=0.20 -> recall=0.93 precision=0.98  (+false alarm)

The program also prints the score separation - lowest P(fraud) among real frauds vs highest among normals. Here the four missed frauds score essentially 0: they are genuinely normal-looking transactions, and no threshold can rescue them. That is the honest lesson: lowering the threshold buys recall from borderline cases only; deeply ambiguous rows need better features, not a different cut-off. In production you would pick the threshold on a validation set according to the cost ratio of missed fraud vs false alarm.
